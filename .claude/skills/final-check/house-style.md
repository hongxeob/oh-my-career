# 한국어 이력서 하우스 스타일 (공용 규칙)

이력서 산문의 "AI 티"를 없애기 위한 프로젝트 공용 규칙.
`draft-resume`와 `refine-resume`는 **작성 시** Tier 1을 지키고, `final-check`는 **검수 시** Tier 1+2를 모두 본다.

적용 범위 구분:
- **산문 구간** = Summary, 커버레터, 회사 소개 블록쿼트, 포트폴리오 서술 → 전 규칙 적용
- **개조식 bullet** = 경력 항목 불렛 → 압축 표기 허용, 아래 표의 "bullet" 열 참조
- **나열 구간** = 스킬 섹션, 회사별 기술 스택 줄 → 아래 「나열 구간은 이름만 쓴다」 참조

---

## Tier 1 — 작성 시 반드시 지킬 것 (draft / refine)

| # | 금지 패턴 | 산문 | bullet | 고치는 법 |
|---|----------|------|--------|----------|
| 1 | 가운뎃점(·) | 금지 | 금지 | **자리와 개수 무관.** 쉼표, `~와/과`, 괄호, 마침표, 슬래시(아래 함정 주의) |
| 2 | Em dash(—)로 절 잇기 | 금지 | 예외: `**제목** — 부제` 헤더 형식만 허용 | 접속사나 연결어미로 문장에 녹임 |
| 3 | 숫자 범위 물결표(`20~30ms`) | 금지 | 금지 | 하이픈(`20-30ms`) — 아래 판별 기준 참조 |
| 4 | 무생물 주어 | 금지 | 금지 | 사람을 주어로. "이 경험은 저를 성장시켰습니다" → "이 경험으로 성장했습니다" |
| 5 | 피동형(`~되었습니다`) | 금지 | 금지 | 능동으로. "응답 시간이 개선되었습니다" → "응답 시간을 개선했습니다" |
| 6 | 과잉 명사화(`최적화를 진행했습니다`) | 금지 | 금지 | 동사 직접. → "최적화했습니다" |
| 7 | `~를 통해` 반복 | 한 문단 2회 이상 금지 | — | 문장 분리 또는 `-며`, `-여`, 쉼표 |

### 나열 구간은 이름만 쓴다 (스킬 섹션, 기술 스택 줄)

**스킬 섹션과 기술 스택 줄에는 기술·제품·표준의 고유명사만 쓴다.** 방법론, 설계 패턴 서술, 성과 표현을 넣지 않는다.

판별은 하나로 한다 — **그 항목이 검색창에 넣었을 때 토큰으로 매칭될 고유명사인가.** 문장이면 뺀다.

| 자리 | 쓰지 말 것 | 대신 |
|---|---|---|
| 스킬 | `컨슈머 그룹 격리와 파티션 전략`, `DLT 폭발 반경 설계`, `offset 기반 재처리` | `Kafka`, `Debezium (CDC)` |
| 스킬 | `통제변수 고정 A/B 검증`, `커넥션 산수 기반 동시성 설계`, `처리량과 CPU 비용 측정` | (뺀다. 경력 bullet의 몫이다) |
| 스킬 | `형태소 분석 기반 다국어 인덱스 설계`, `alias 무중단 인덱스 전환`, `CQRS 읽기 모델 설계` | `OpenSearch`, `Elasticsearch` |
| 스킬 | `팀 공통 플러그인 설계와 배포`, `문서 자동 동기화 파이프라인 팀 전파` | (뺀다. 경력 bullet의 몫이다) |

허용되는 예외는 **동의어나 약어를 괄호로 붙이는 것**뿐이다 (`Debezium (CDC)`, `AWS (EC2, RDS, S3, Lambda)`).

⚠️ **왜 이 규칙이 필요한가** — 파이프라인이 반복해서 여기에 부가 설명을 달았다. 두 가지가 동시에 망가진다.
① 그 서술은 **경력 bullet에 이미 있어서 중복**이고 ② 채용자는 스킬 섹션을 **스캔 목록**으로 읽는데
문장이 섞이면 스캔이 멈춘다. 역량을 보여주는 자리는 경력 bullet이고, 스킬 섹션은 **색인**이다.

카테고리 라벨은 JD가 무게를 두는 순서대로 배치한다(파이프라인 포지션이면 `Data Pipeline`이 `Language`보다 앞).

### 물결표 판별 기준 (공백 유무로 판단하지 말 것)

물결표를 하이픈으로 바꿔야 하는지는 **양쪽이 무엇이냐**로 판단한다. 공백은 신뢰할 수 없는 기준이다(`4~5시간`과 `4 ~ 5시간`이 같은 성격인데 갈린다).

| 양쪽 | 예 | 처리 |
|------|----|------|
| 숫자 범위(단위, 수량, 기간 길이) | `20~30ms`, `4~5시간`, `3~5건` | **하이픈으로** (`20-30ms`) |
| 날짜나 기간의 시작과 끝 | `2025.06 ~ 현재`, `2024.04 ~ 2025.06` | **그대로 둔다** |

이유: 마크다운 뷰어가 `~텍스트~`를 취소선으로 오인하는데, 날짜 범위는 양쪽에 마침표나 한글이 붙어 트리거되지 않는다.

### 가운뎃점은 예외 없이 안 쓴다 (2026-09 개정)

**소제목, 표 셀, 링크 앞 구분자까지 전부 포함한다.** 규칙에 자리 구분을 두면 그 틈으로 새어 나간다.

원래는 bullet에서 2개 연쇄까지 허용했고 소제목은 규정이 없었다. 그 빈칸으로 `데이터 서빙 API · 성능`,
`정합성·안정성` 같은 표기가 제출본까지 갔다. **AI가 쓴 티가 나는 문자**라 개수와 무관하게 쓰지 않는다.

| 자리 | 전 | 후 |
|---|---|---|
| 소제목 | `데이터 서빙 API · 성능` | `데이터 서빙 API와 성능` |
| bullet 볼드 | `**정합성·안정성**` | `**정합성과 안정성**` |
| 링크 앞 구분자 | `... 단건 통합 · [상세]` | `... 단건 통합. [상세 기록]` |
| 회사 헤더 | `백엔드팀 · 전시/검색 스쿼드` | `백엔드팀 (전시/검색 스쿼드)` |

### ⚠️ 가운뎃점 → 슬래시 치환 함정

가운뎃점은 한국어에서 **AND**로도 쓰이는데 슬래시는 통상 **OR**로 읽힌다.

- `재구축·운영`(재구축하고 운영함) → `재구축/운영`으로 바꾸면 "둘 중 하나만"으로 의미가 뒤집힌다
- **동사를 잇는 가운뎃점** → `및`, `하고`, 쉼표로
- **진짜 병렬 명사**(`웹/앱`, `검색/전시`, `한국어/일본어/영어`처럼 애초에 "또는" 계열 의미) → 슬래시로

`sed` 등으로 일괄 치환한 뒤에는 **반드시 각 줄을 다시 읽어** 의미가 뒤집힌 곳이 없는지 확인한다.

### Summary는 처음 보는 사람 기준으로 쓴다 (2026-09 추가)

Summary를 먼저 읽는 사람은 **우리 서비스도 사내 사정도 모르는 채용 담당자**다. bullet은 정확한 수치를 그대로 두지만,
**사내 용어는 bullet에서도 풀어 쓴다** (아래 「본문 bullet도 사내 용어를 풀어 쓴다」). **같은 성과라도 Summary와 bullet에는 쓰는 방식이 다르다.**

| # | 금지 | 이유 | 대신 |
|---|------|------|------|
| S1 | **사내 맥락 용어** (서비스 고유 기능명, 사내 이벤트명) | 채용자는 그게 얼마나 큰지, 왜 문제인지 모른다 | 일반적인 대비 구도로 쓴다. 예: `월말 마감 배치` → `대량 일괄 처리 ↔ 실시간 결제 처리` |
| S2 | **기준 없는 원시 수치** (단위 없는 건수, 작은 분모의 비율) | 많은 건지 잘 줄인 건지 판단할 수 없다. 작은 분모는 "표본이 적네"로 읽힌다 | 사람이 체감하는 단위(분 단위 지연, "재시작이나 다운 한 번에 사라지던")나 직관적 비율(절반)을 쓴다. 정확한 수치는 bullet에 둔다 |
| S3 | **예시 나열** (`가격과 재고 같은`) | 첫인상에 정보가 늘지 않고 문장만 길어진다 | 뺀다 |
| S4 | **`-고` 연결과 복문** | 한 문장에 성과 두세 개가 매달려 읽다가 놓친다 | 한 문장에 성과 하나. 마침표로 끊는다 |
| S5 | **절차와 방법론 용어** (`반대 가설 배제`, `교차 지표`) | 엔지니어 말이라 채용자에게는 소음이다 | 태도 한 줄로 바꾼다. 예: "기준선을 잘못 잡은 제 성과 수치를 스스로 철회한 적도 있습니다" |
| S6 | **정확하지 않은 전문 용어** | 틀린 용어는 면접 첫 질문이 된다. 예: 큐 경합(HOL)을 "백프레셔"로 쓰는 것. 백프레셔는 하류가 상류 속도를 늦추는 흐름 제어라 뜻이 다르다 | Summary는 쉬운 말("막혀", "밀리던"), 정확한 용어는 bullet에 |
| S7 | **시스템 능력으로 읽히는 요구 표현** | `실시간 증분 변경`은 5초 주기 배치(Near Real-Time) 시스템을 실시간 스트림 처리 경험으로 넓힌다 | 변경의 요구 조건으로 쓴다: `실시간 반영이 필요한 증분 변경` |
| S8 | **회사 문화 문구 인용** (`"모호한 감을 명료한 확신으로"`) | 공고 문구를 되돌려주는 건 증거가 아니다. 분량만 쓴다 | 뺀다. 연결은 면접에서 |

**판별 질문 하나:** "이 회사 공고만 읽은 사람이 이 문장을 한 번 읽고 무슨 문제를 얼마나 풀었는지 말할 수 있는가?"
말할 수 없으면 고친다.

예시(가상 인물 김개발): `정산 대기열 적체 최댓값을 8,400에서 0으로`, `타임아웃이 관측 21회 중 12회에서
적용 후 3회 중 0회로`는 둘 다 귀속과 값이 정확해도 처음 보는 채용 담당자는 공감하지 못한다. Summary에는
`월말마다 정산이 몇 시간씩 밀리던`처럼 체감 단위로 쓰고, 정확한 수치는 bullet에 남긴다.

### 본문 bullet도 사내 용어를 풀어 쓴다 (2026-10 추가)

판별: **"우리 회사 밖 사람이 배경 설명 없이 알아듣는가."** 못 알아들으면 괄호 풀이나 일반어로 바꾼다.
표준 기술 용어(Kafka, CDC, offset, Circuit Breaker)는 그대로 둔다.

| 종류 | 전 (가상 예) | 후 |
|---|---|---|
| 사내 기능명, 콘텐츠명 | `코디북 인덱스`, `피치딜` | `코디(스타일 큐레이션) 인덱스`, `한정 특가` |
| 사내 시스템, 팀 별칭 | `블루 서버`, `정산 레인` | `정산 서버`, `정산 전용 경로` |
| 인프라 단위, 사내 약어 | `pod당`, `올인원 API` | `서버 인스턴스당`, `상세까지 한 번에 내려주던 API` |
| 명령어, 함수 이름 수준 | `ZADD NX`, `ZPOPMIN` | `Redis에 ID만 모아(같은 ID는 하나로)` |
| 사내 이벤트, 운영 작업명 | `피치위크 반영`, `피치딜 매핑 작업` | 업계 공용어로 바꾼다: `대량 일괄 작업`, `대량 변경 버스트`, `실시간 반영이 필요한 단건 변경`. ⚠️ `대량 일괄 색인`은 업계에서 전체 재색인(백필)으로 읽히니, 실제로 몰려 들어온 변경 이벤트였다면 쓰지 않는다. 바꾼 뒤에는 **무엇을 떼어 냈고 무엇이 느려졌는지 대상이 원본과 같은지** 다시 본다(넓은 말로 바꾸면 대상도 같이 넓어진다). 괄호 풀이(`피치위크(할인 행사)`)로 버티지 않는다. 풀이가 붙어도 "그게 왜 대량인지"는 여전히 사내 맥락이다 |

⚠️ **풀이에 원본에 없는 주어, 대상, 원인을 채우지 않는다.** 원본이 "A 쪽을 떼어 냈다"인데 풀면서 B로 바꾸면
cross-verify에서 오귀속이 난다(실제로 BLOCK이 났다). 뜻을 모르면 풀지 말고 원본 표현을 쓴다.

### Summary 구성: 성과 요약이 아니라 "어떤 개발자인가" (2026-10 추가)

**성과 bullet을 줄인 문장 4개를 늘어놓지 않는다.** 그러면 첫 화면에 본문과 같은 말이 두 번 나오고, 정작
"어떤 개발자인가"가 없다. 산문(습니다체) 3-4문장, 링크드인 소개처럼 사람이 읽히되 문장마다 본문 근거가 있어야 한다.

| 순서 | 역할 | 쓰는 법 |
|---|---|---|
| 1 | **정체성** | 거쳐 온 도메인 → 지금 무엇을 하는 사람인가. `~하는 백엔드 엔지니어입니다`로 끝낸다. 지원 회사가 풀고 싶은 문제와 닿는 말로 |
| 2 | **근거** | 어디서 무엇을 해 왔나. 성과는 숫자 없이 종류로("반영 지연과 CPU 경합을 하나씩 줄여 왔습니다"). 2인 성과와 단독 성과를 한 주어에 묶지 않는다. 정확한 수치는 바로 아래 bullet이 맡는다 |
| 3 | **일하는 방식** | 무엇에 가치를 두고 어떻게 판단하나. 본문 사실(실측, A/B, 전수 비교, 트레이드오프)에서 뽑는다 |
| 4 | **회사가 찾는 결** | 아래 「4번 문장의 결은 회사가 정한다」에 따라 고른다. 어느 쪽이든 형용사("적극적인", "깊이 있는") 대신 **본문 사실**로 보여준다 |

#### 4번 문장의 결은 회사가 정한다 (2026-10 추가)

**적극성을 기본값으로 넣지 않는다.** `/evaluate-jd`가 JD와 회사 신호(문화 시그널, 리더 인터뷰, 기술 블로그)를 보고 아래 중 하나를 고르고, 「이력서 커스터마이징 가이드」의 Summary 방향에 적는다. draft, refine은 그 값을 따른다.

| 결 | 이런 신호가 보이면 | 3, 4번 문장에 쓰는 본문 사실 |
|---|---|---|
| **오너십, 적극성** | "문제를 정의하는 사람", "초기 멤버", "직접 책임", "정답이 없다" (예: 초기 단계 조직, 신규 사업) | 담당 밖의 도구를 직접 만든 것, 팀 전체로 넓힌 것, 단독으로 키운 것 |
| **기술 깊이, 트레이드오프** | "원리를 이해", "트레이드오프", "정합성 보장 방식", "대용량에서 검증" (예: 금융, 대용량 거래 시스템) | 선택지와 기각 이유, 대가를 함께 기록한 것, 실측으로 가설을 걸러낸 것 |
| **협업, 제품 감각** | "유관 부서와", "사용자 경험", "PM, 디자이너와" | 타 직군 요구사항을 직접 뽑은 것, 반복 문의를 구조로 없앤 것 |

둘이 섞이면 JD 필수 요건 쪽을 4번에, 다른 하나를 3번에 반 문장으로 둔다. 판단 근거(어느 문구를 봤는지)를 evaluate 리포트에 한 줄 남긴다.
**동기나 의도를 지어내지 않는다.** "맡은 범위 밖이라도"처럼 원본에 없는 동기를 쓰면 cross-verify D축에서 ❌가 난다(실제로 BLOCK이 났다). 범위 밖이었다는 건 사실("결제 서버 담당이지만")로 보여준다.

- 기여도는 고정 문장을 넣지 않고 `테크리드와 함께`, `단독으로 주도`처럼 짧게만 (고정 문장은 회사 블록에)
- **근거 없는 수사는 뺀다**: "흥미를 느끼며", "함께 성장하는 것을 좋아합니다", "열정". 링크드인에는 맞아도 이력서에서는 건너뛴다

예시(가상 인물 김개발, 형식만 본다):

> 커머스 주문 도메인을 거쳐, 지금은 핀테크 서비스에서 결제와 정산이 빠르고 틀림없이 처리되도록 시스템을 설계하고 운영하는 백엔드 엔지니어입니다. 팀원과 함께 모놀리식 정산 시스템을 이벤트 기반으로 나눴고, 이후 결제 처리 경로를 맡아 느린 응답과 중복 결제를 하나씩 줄여 왔습니다. 정합성과 처리 속도 사이의 트레이드오프를 실측으로 확인하며, 요구사항에 맞는 단순한 구조를 고르는 데 가치를 둡니다. 결제 서버 담당이지만 운영팀이 반복해서 요청하던 정산 대사 작업을 도구로 만들어 개발자 없이 돌리게 했습니다.

- 2번 문장: 공동 성과("팀원과 함께")와 단독 성과("이후 ... 맡아")를 주어로 갈랐다. 한 주어에 묶으면 오귀속이다
- 4번 문장: "범위 밖이라도" 같은 동기 대신 "결제 서버 담당이지만"이라는 사실로 보여준다
- 반례: "응답 80% 단축, 레이스 컨디션 0건, 배포 주기 3배"처럼 성과를 늘어놓으면 본문 축약이 되어 사람이 안 보인다

**회사마다 1번 문장의 "무엇을 하는 사람인가"만 그 회사 문제 쪽으로 바꾸고, 뼈대는 유지한다.**

## Tier 2 — 검수 시 추가 탐지 (final-check 전용)

- **시제와 어미 통일**: 개조식으로 통일됐는지, 문장형이 섞여 있지 않은지
- **동사 다양성**: 같은 동사(`개선했다`, `구축했다`)가 연속 반복되는지
- **한 줄 안 어휘 반복**: 같은 단어가 한 문장이나 한 bullet 안에서 두 번 나오는지.
  Tier 1 스캔은 정규식으로 잡히는 패턴만 보므로 이건 걸리지 않는다. 눈으로 읽어야 한다
  (실제 사례: `반대 가설부터 기각 — …으로 기각`, `대가도 함께 기록 — 이 대가와`, `흩어진 원본을 원본 테이블 구조와`)
- **제목 형식 통일**: bullet 제목의 종결이 명사형으로 통일됐는지, 1인칭(`제`, `내`)이 섞이지 않았는지
- **오탈자**
- **키워드 스터핑**: JD 키워드를 억지로 밀어넣어 부자연스러운 구간

검수 시 지적 방식은 **일반론 금지** — 반드시 원문을 인용한 뒤 고친 문장을 함께 제시한다.
개조식 bullet에는 산문 윤문을 적용하지 않는다(지적만 한다).
