# draft-resume

## Overview

원본 커리어 데이터(팩트)와 JD를 분석해 **전략이 다른 3가지 이력서 초안**을 생성한다.
원본 데이터는 절대 변형하지 않는다 — 표현 방식만 달리한다.

## Input

> `{RESUME}`과 `{JD}`가 **어느 디렉토리에 있는지는 CLAUDE.md 「경로 해석」에만 적혀 있다.** 파일명은 바뀌지 않지만 위치는 바뀐다. 못 찾으면 스킬이 아니라 그 표를 고친다.

**기본 경로** (oh-my-career 프로젝트):
- 원본 이력서: `{RESUME}` (`my-resume.md`)
- JD: `{JD}` (`{company}_jd.md`)
- **평가 리포트 (있으면 반드시)**: `outcome/{company}/0_evaluate/{company}-evaluate.md` — **두 섹션만** 읽는다
  ```bash
  sed -n '/^## \(Step 1\. \)\?JD 핵심 요건/,/^## [^J]/p'   outcome/{company}/0_evaluate/{company}-evaluate.md
  sed -n '/^## 이력서 커스터마이징 가이드/,/^## 예상 면접 질문/p' outcome/{company}/0_evaluate/{company}-evaluate.md
  ```
  리포트 전문은 50KB에 육박하는데 이 단계에 필요한 건 13KB다. 예상 면접 질문과 스코어카드는 `/story-bank` 몫이다
- 출력: `outcome/{company}/1_draft/{company}-draft-{A|B|C}.md`

다른 파일을 쓰는 경우 사용자에게 경로를 확인하라.

## Process

### Step 1: JD 분석 (평가 리포트가 있으면 재사용한다)

**`/evaluate-jd`가 이미 이 JD를 분해해놨다면 다시 분해하지 않는다.** 같은 판단을 두 번 하면 두 결과가
달라져도 아무도 모른다. 평가 리포트의 「JD 핵심 요건 추출」 표를 그대로 가져오고, 아래 표에서 **비어 있는
칸만** JD에서 보강한다(보통 `측정 지표` 하나다).

| 구분 | 내용 | 출처 |
|------|------|------|
| 핵심 역할 | 이 포지션이 실제로 하는 일 | 평가 리포트 |
| 필수 스킬 | must-have 요건 | 평가 리포트 |
| 우대 스킬 | nice-to-have 요건 | 평가 리포트 |
| 키워드 | ATS에 걸릴 핵심 단어들 | 평가 리포트 |
| 문화 시그널 | 회사/팀 문화를 나타내는 표현 | 평가 리포트 |
| 측정 지표 | 성과를 어떻게 측정하는지 | **JD에서 보강** |

「이력서 커스터마이징 가이드」의 *강조할 포인트 / 뺄 포인트 / Summary 방향*은 **A/B/C 전략 선택의 입력으로 쓴다.**
평가 단계가 "이 불렛을 상단에, 이 표현을 이렇게"까지 만들어놨는데 초안이 그걸 안 읽으면 그 작업은 버려진다.

평가 리포트가 없으면(0단계를 건너뛴 경우) 위 6행을 JD에서 직접 뽑는다.

### Step 2: 원본 데이터 파싱 → **팩트 블록** 만들기

원본에서 **팩트만** 추출 — 해석하지 않는다:

```
[회사] [기간] [직책]
- 실제 수행한 업무 (원문 그대로)
- 실제 달성한 수치 (원문 그대로)
- 실제 사용한 기술 (원문 그대로)
```

**이 결과물이 Step 3에서 세 에이전트에게 그대로 넘어간다.** 그러니 여기서 두 가지를 지킨다:

- **원문 그대로 옮긴다.** 여기서 요약하거나 수치를 다듬으면 세 버전이 전부 그 왜곡 위에 서고,
  `/verify-resume`와 `/cross-verify`가 잡아야 할 오귀속을 이 단계가 만들어 넣는 셈이 된다
- 원본 상단 **세 블록을 전부 팩트 블록에 넣는다** — ⚠️ 수치 귀속표, 🧭 **시스템 경계**, 🚫 인용 금지 목록.
  줄 번호는 `grep -n '수치 귀속표\|시스템 경계\|인용 금지 목록' "$RESUME"`로 찾는다.
  **시스템 경계를 빼지 마라.** 실제로 난 사고가 정확히 시스템 경계 위반이었다 — 어느 수치가 어느 시스템에
  붙는지 모르는 채로 쓰면 그 사고를 초안 단계에서 만들어 넣는다. 나중에 잡는 것보다 안 만드는 게 싸다

### Step 3: 세 버전을 서브 에이전트로 **동시에** 생성한다

`Agent` 도구를 **한 메시지에 3개 호출**한다(`subagent_type`은 `general-purpose`). 세 버전은 서로를 참조하지
않는다 — "동일한 팩트, 다른 강조점"이라 순차로 쓸 이유가 없다. 순차로 쓰면 이력서 본문 분량을 세 번 연달아
생성하게 되고, 이 스킬이 파이프라인에서 출력이 가장 많은 단계다.

**각 에이전트에 넘기는 것 (셋 다 동일 + 자기 전략):**

1. Step 1의 JD 분석 표와 커스터마이징 가이드 요약
2. **Step 2에서 뽑은 팩트 블록** — 원본 파일 경로가 아니라 추출한 팩트를 넘긴다.
   45KB 원본을 셋에게 각각 읽히면 135KB가 된다. Step 2의 팩트 블록은 그 1/3이고, 셋이 **같은 팩트**를
   봐야 세 버전이 같은 사실 위에 서게 된다
3. 그 에이전트의 전략 하나
4. **경계 지시**: "다른 두 버전은 {X}, {Y} 전략을 맡는다. 그 영역은 침범하지 마라"
5. `.claude/skills/final-check/house-style.md` 경로 (각자 읽고 Tier 1 적용)

⚠️ **원본에 없는 숫자를 만들지 말라는 규칙을 각 프롬프트에 그대로 넣는다.** 서브 에이전트는 이 SKILL.md의
Critical Rules를 보지 못한다.

**세 전략 (각 에이전트에 하나씩):**

---

#### Version A: ATS 최적화형 (키워드 밀도 우선)

**전략:** JD 키워드를 자연스럽게 포함, ATS 통과 최적화

- Summary: JD 언어를 직접 반영, 역할 타이틀 포함
- 경험 bullets: JD 필수/우대 스킬과 1:1 매핑
- 스킬 섹션: JD 키워드 순서대로 나열
- **금지:** JD에 없는 신조어, 과도한 수식어

---

#### Version B: 임팩트 중심형 (수치/성과 우선)

**전략:** 모든 bullets를 수치화된 성과로 시작

- Summary: 가장 강력한 성과 2개로 시작
- 경험 bullets: "동사 + **원본에 있는** 수치 + 임팩트" 구조 강제
  - ❌ 약함: 행동만 있고 결과가 없는 문장("~에 기여", "~을 담당")
  - ✅ 강함: 무엇이 얼마에서 얼마로 바뀌었는지가 한 줄에 들어간 문장
  - ⚠️ 예시 수치를 이 파일에 적어두지 않는다 — 다른 사람 데이터가 초안에 새어 든다
- 수치가 없으면: 규모(팀 크기, 사용자 수, 기간)로 대체
- 스킬 섹션: 성과와 연결된 기술만

---

#### Version C: 스토리텔링형 (문화핏 우선)

**전략:** 성장 서사와 회사 문화 정렬

- Summary: "왜 이 회사인가" 연결되는 개인 비전
- 경험 bullets: 문제 상황 → 내 역할 → 결과의 서사
- 회사 문화 시그널 언어 자연스럽게 반영
- 팀워크, 리더십, 오너십 경험 부각

---

### Step 4: 전략 차별화 확인 후 한 번에 저장

세 에이전트가 서로를 못 봤으므로 **오케스트레이터가 겹침을 확인한다.** 전문을 재검토하지 말고
**Summary 세 개만 나란히 비교**한다 — 전략이 갈렸으면 여기서 갈린다. 셋이 비슷하게 읽히면 그 버전만
경계 지시를 강화해 다시 띄운다.

확인 후 `Write` 3개를 **한 메시지에** 호출해 저장한다:
`outcome/{company}/1_draft/{company}-draft-{A|B|C}.md`

### Step 5: 초안 구조 (각 에이전트가 지킬 형식)

⚠️ **완성된 초안 3벌을 대화창에 다시 출력하지 않는다.** 파일에 있고, 사용자는 어차피 verify 리포트의
"추천 버전"으로 고른다. 대화창에는 **버전별 전략 1줄 + 파일 경로**만 낸다.

각 에이전트는 다음 구조로 작성한다:

```markdown
## Version [A/B/C]: [전략명]
**타겟 강점:** [한 줄 전략 설명]

### 헤더
이름 | 연락처 | 링크

### Summary (3-4문장)
...

### 경력
**[회사명]** | [팀] · [직책] | [기간]

> [회사/서비스 한 줄 소개 — 원본에 있는 사실만]

- ...

**기술 스택**: `기술` `기술` ...

### 스킬
...
```

⚠️ **블록쿼트 소개와 회사별 기술 스택 줄을 초안 단계에서 이미 넣는다.** `/refine-resume` Step 3.5가 이 두 요소를 필수로 요구하므로, 초안에 없으면 refine에서 전 경력 항목을 재구조화해야 한다.

저장 후 대화창에는 각 버전의 **전략적 의도 1줄 요약과 파일 경로**만 낸다.

## Critical Rules

- 원본에 없는 숫자/사실을 생성하지 않는다 (→ /verify-resume가 검증)
- 세 버전은 전략이 달라야 한다 — 단어만 바꾸는 것은 금지
- JD와 무관한 경험은 압축하거나 제거한다
- 생성 후 반드시 `/verify-resume` 실행을 안내한다

### 하우스 스타일 (작성 시 준수 — 뒤에서 재작업 방지)

`.claude/skills/final-check/house-style.md`를 읽고 **Tier 1 전 항목**을 적용한다.

⚠️ **금지 패턴 목록을 이 파일에 복사해두지 않는다.** 사본을 두면 house-style이 개정돼도 여기가 안 따라오고,
초안 단계가 폐기된 규칙으로 문서를 만든다. 실제로 그렇게 샜다 — house-style이 가운뎃점을 전면 금지한 뒤에도
이 자리에 "3개 이상 연쇄만 피한다"는 옛 사본이 남아 제출본까지 갔다.

## Next Step

```
✅ 3가지 초안 저장 완료
  → outcome/{company}/1_draft/{company}-draft-A.md
  → outcome/{company}/1_draft/{company}-draft-B.md
  → outcome/{company}/1_draft/{company}-draft-C.md
▶ **이어서 /verify-resume 를 바로 실행한다.** 사용자에게 묻지 않는다.
```

> **이어달리기 규칙 (앞 구간만)** — 파이프라인은 **`/review-resume`까지만** 자동으로 이어진다.
> `draft → verify → cross-verify → review`는 전부 **리포트만 내는 단계**라 사람이 볼 게 없다.
>
> **`/refine-resume`부터는 사용자가 직접 호출한다.** refine, final-check, pdf는 제출본 문장을 다시 쓰거나
> 제출본을 확정하는 단계다. 사고는 전부 이 뒤쪽 구간에서 났다 — 오귀속, 게이트 우회, 게이트에서
> 떨어진 PDF가 "지원 완료"로 기록된 것 전부.
>
> 중간에 사용자가 끼어들면 그 지시가 우선한다.
